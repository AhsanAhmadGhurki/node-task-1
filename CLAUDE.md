# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Two separate apps:
- **`backend/`**: Tasks REST API built on Express 5 + Mongoose 9 (MongoDB), CommonJS, with JWT auth (bcryptjs + jsonwebtoken). No build step, linter, or test suite.
- **`frontend/`**: React + Vite SPA (ESM) with react-router v7 and axios, for using register, login, resend verification and task CRUD in the browser.

## Commands

Backend (run from `backend/`):
- `npm run dev`: run with `node --watch` (auto-restart on file changes)
- `npm start`: run normally

Both use Node's built-in `--env-file=.env` (no dotenv package), so `backend/.env` must exist with `PORT` (default 3000), `MONGO_URI`, `API_KEY` and `JWT_SECRET`, plus the optional `SMTP_USER` and `SMTP_PASS` for real emails.

Frontend (run from `frontend/`):
- `npm run dev`: Vite dev server on http://localhost:5173
- `npm run build`, `npm run lint` (oxlint)

`frontend/.env` must contain `API_KEY` with the same value as the backend's.

Every API request needs an `x-api-key` header. `/tasks` routes also need `Authorization: Bearer <token>` from `POST /auth/login`:
```
curl -H "x-api-key: $API_KEY" -H "Authorization: Bearer $TOKEN" http://localhost:3000/tasks
```

## Frontend structure

Under `frontend/src/`, the layers mirror the backend:
- **`api/`**: `axios.js` is the single axios instance (`baseURL: '/api'`). A request interceptor reads the token **directly from `localStorage`** through `utils/helpers.loadSession()`, not from context: React runs child effects before parent effects, so Dashboard's first request would otherwise go out without a token. Before each request, if the access token has expired it refreshes first. On a 401 for a request that carried a token, it refreshes once (`_retried`) and retries. Refresh is **single-flight** (a shared `refreshPromise`), so parallel 401s trigger one refresh; the old token would be rotated away otherwise. Refresh uses bare `axios.post('/api/auth/refresh')`, which skips the interceptors. If the refresh fails, it calls `onUnauthorized` (registered via `setAuthHandlers`). A 401 on login (wrong password) has no token, so it never refreshes. `utils/helpers.loadSession()` keeps sessions whose access token has expired, because refresh can revive them. `authApi.js` and `taskApi.js` are thin wrappers that return `data`.
- **`context/AuthContext.jsx`**: `AuthProvider` (session state, `login`, `logout(reason)`, `notice`). It registers `onRefreshed` (updates state) and `onUnauthorized` (clears the local session with a "Session expired" notice). User-initiated `logout()` also calls `POST /auth/logout`. The context object and the `useAuth()` hook live in `hooks/useAuth.js`; keeping them out of the provider file keeps Vite fast refresh working (oxlint `only-export-components`).
- **`pages/`**: `Login`, `Register`, `Dashboard` and `NotFound`. Routes are in `App.jsx`: `/` redirects to `/dashboard`, which is wrapped in `components/ProtectedRoute`, which redirects to `/login` when there's no token. Login and Register redirect to `/dashboard` when already logged in.
- **`components/`**: `Navbar`, `TaskItem`, `TaskForm`, `Loader`, `Alert` (`{ ok, status, text }`, built by `helpers.toAlert(error)`), and `ResendVerification` (shown after register, on a 409, or on a 403 login).
- **Dashboard:** every mutation goes through `run()`, which sets `busy` (disables buttons, so one click sends one request) and turns errors into an `Alert`. The first load in `useEffect` sets state only in `.then` and has a `cancelled` cleanup (oxlint `set-state-in-effect`). In dev, StrictMode sends the first `GET /tasks` twice; that's expected.

## Frontend ↔ backend

The browser never calls `localhost:3000` directly. `frontend/src/api/axios.js` calls `/api/...`, and the Vite proxy in `frontend/vite.config.js` strips `/api`, forwards the request to the backend, rewrites the refresh cookie path (`cookiePathRewrite: { '/auth': '/api/auth' }`, otherwise the browser never sends it to `/api/auth/refresh`), and **adds the `x-api-key` header server-side** (read with `loadEnv` and no `VITE_` prefix). Because of this, the backend has no CORS middleware and the API key never reaches the browser bundle. Don't expose it with a `VITE_` variable.

## Backend architecture

Layered flow: `routes → (validation middleware) → controllers → services → models`. All paths below are under `backend/src/`.

- **`index.js`** first runs `config/validateEnv.js`, which checks for required `MONGO_URI`, `API_KEY` and `JWT_SECRET` (both at least 32 characters; generate the API key with `openssl rand -hex 32`), that `SMTP_USER` and `SMTP_PASS` are set together, that `MONGO_URI` starts with `mongodb://` or `mongodb+srv://`, that `PORT` and `SMTP_PORT` (when set) are integers from 1 to 65535 (an invalid value never silently falls back to the default), and that `APP_URL` is valid. It lists every problem and exits with code 1 before any DB connection. After that it connects to MongoDB, then starts the server, each in its own `try`, so a port error is never reported as "MongoDB connection failed". It exits the process if either step fails. **`app.js`** only builds the Express app, so it can be imported without starting a server.
- **Middleware order in `app.js` matters:** `helmet()` (security headers; first, so a malformed-JSON 400 from `express.json` still gets them) → `express.json` → `cookieParser` → logger → `GET /verify/:token` (public, mounted before the API key check because the link is opened in a browser without headers) → API key check (global, after the logger so rejected requests still get logged) → `/tasks` (with `authMiddleware`) → `authRoutes`, mounted at the root with full paths: `POST /register` and `POST /auth/login` (no JWT check, since login is where the token is issued) → `POST /resend-verification` → 404 handler → central error handler (always last).
- **Auth:** `services/authService.js` hashes passwords with bcrypt on register, and on login compares the password and signs a 15-minute access JWT with `{ sub: user.id }`. **Refresh tokens:** login also issues a random 32-byte refresh token. It's stored as a SHA-256 hash in `models/RefreshToken.js` (7 days, with a TTL index for cleanup) and sent only as an httpOnly, `SameSite=Strict`, `Path=/auth` cookie, never in the JSON body (`cookie-parser`). `POST /auth/refresh` rotates the token: it atomically revokes the old one, then issues a new access token and a new refresh token. If a revoked token comes back more than 30s after it was revoked (`REFRESH_REUSE_GRACE_MS`), that's treated as theft and revokes all of the user's refresh tokens. Within the 30s it's treated as a multi-tab race. A failed refresh deliberately does **not** clear the cookie, so a losing tab can't wipe the winner's new cookie. `POST /auth/logout` revokes the token and clears the cookie. `middleware/auth.js` verifies `Bearer` tokens: the signature against `JWT_SECRET`, `algorithms: ["HS256"]` only (so `none`, HS384/512 and RS256 are rejected), and expiry. It also **requires** `exp` and a `sub` that looks like an ObjectId (24 hex characters), because `jwt.verify` alone accepts tokens without `exp`. `signAccessToken` sets `algorithm: "HS256"` explicitly, to match. It then sets `req.user = { id }`. The `User` model's `toJSON` removes `password`, so it's safe to return user documents. Login gives the same 401 message for an unknown email and a wrong password.
- **Email verification:** register uses `validateRegister` (8+ characters, at least one digit; login keeps the looser `validateAuth`) and bcrypt cost 12. It stores `isVerified: false`, plus `verificationTokenHash` (the SHA-256 of a `crypto.randomBytes(32)` hex token) and `verificationTokenExpires` (24h). The raw token exists only in the link, which `services/emailService.js` prints to the console **only when SMTP is not configured** (labelled `[dev — SMTP not configured]`; with SMTP the raw token is never logged, and `middleware/logger.js` masks `/verify/<token>` in request logs) (`${APP_URL}/verify/<token>`; `config.appUrl` comes from `APP_URL`, falls back to `http://localhost:${PORT}`, and has any trailing slash removed) and also emails through Nodemailer when `SMTP_USER`/`SMTP_PASS` are set (default host `smtp.gmail.com:465`, configured in `config.smtp`). Register and resend call it without `await`, so the response doesn't wait for SMTP (which takes 1–4s). A failed send is logged, not thrown, so this never causes an unhandled rejection. SMTP gives up after a 10s connection timeout, and an App Password pasted with spaces gets the spaces stripped in config. On verify, a malformed token gives 400; an unknown, used or replaced token gives 410; an expired one gives 410. Success sets `isVerified` and `$unset`s both token fields through an atomic `updateOne`. The verify controller uses `res.format`: browsers (`Accept: text/html`) get a small HTML page from `views/verifyPage.js` with the same status code, and API clients get `{ message }` JSON. Resend overwrites the hash, so the old link stops working. Failed verify pages include a resend form that posts to the public `POST /verify/resend` (urlencoded, mounted before the API key check). It shares the controller and `validateEmail` with `POST /resend-verification`. `views/verifyPage.js` exports `respondPage(res, status, {...})`, which sends an HTML page to browsers and `{ message }` JSON to everyone else; the verify and resend controllers and `validateEmail` all use it. **Rate limiting:** `middleware/rateLimit.js` (express-rate-limit, in-memory, keyed by IP) gives `resendLimiter` 5 per 15 minutes, shared by both resend routes, and `registerLimiter` 10 per hour, and `loginLimiter` 10 *failed* logins per 15 minutes (`skipSuccessfulRequests`, mounted before `validateAuth`). All return 429 through `respondPage`. On top of that, a 60s per-email cooldown is stored in `User.verificationEmailSentAt` and checked atomically in `resendVerification`; during the cooldown no email is sent, but the response is not a 429. **Resend always returns the same 200 message** (`RESEND_RESPONSE`) for an unknown email, an already-verified account, a sent email and an active cooldown, so it can't be used to discover which emails are registered or verified. Behind a reverse proxy in production, set Express `trust proxy`, or every client shares one IP. Login returns 403 for unverified users. The check runs after the password check, so a wrong password still gives the generic 401 and does not reveal verification status.
- **Config:** `process.env` is read only in `config/index.js`. Everything else imports that config module.
- **Separation of concerns:** controllers handle req/res and never touch Mongoose. All DB access goes through `services/`.
- **Error handling:** controllers wrap their logic in try/catch and call `next(err)`. Services and middleware throw the Error subclasses in `utils/` (`BadRequestError` 400, `UnauthorizedError` 401, `ForbiddenError` 403, `NotFoundError` 404, `ConflictError` 409, `GoneError` 410, `TooManyRequestsError` 429), each carrying a `statusCode`. `middleware/errorHandler.js` turns malformed JSON bodies (`err.type === "entity.parse.failed"`) into a generic 400 "Invalid JSON in request body"; never echo that error's message, because Node's JSON parse errors include parts of the body, such as the password. It maps Mongoose `CastError` to `Invalid <path>`, and `ValidationError` to per-field messages (a `required` field keeps its own message; everything else becomes `Invalid <path>`, **never `err.message`**, because Mongoose embeds the rejected value, such as a password). MongoDB duplicate-key errors (`11000`) become a fixed 409. `err.message` is sent only for 4xx errors with a `statusCode`, meaning our own classes or body-parser. Everything else gets a generic 500 "Internal Server Error"; the server log records only the error name and stack frames, not the message. Every error response has the shape `{ message }`.
- **Validation is two-layered:** `middleware/validation.js` checks request bodies before they reach the controller (`validateCreateTask`, `validateUpdateTask` for PUT, `validateAuth` for login, `validateRegister`, `validateEmail` for resend). Auth fields go through `stringFieldError()`: missing, `null` or empty gives "<Field> is required", and a non-string (object, array, number, or an operator like `{ "$ne": null }`) gives "<Field> must be a string". Register and resend share `emailError()`, which needs the simple `x@y.z` shape; login doesn't check the format, since a bad email just gets 401. The Mongoose schema rules also apply on updates because `findOneAndUpdate` is called with `runValidators: true`.
- **Express 5 specifics:** `req.body` is `undefined` when no body is sent, so code guards with `req.body || {}`. `app.listen` reports startup errors (such as a port already in use) through its callback's `error` argument.
- **Partial updates:** PUT only changes fields that are `!== undefined`, so `completed: false` still counts as a real update. `validateUpdateTask` requires at least one of `title`/`completed`. Both task validators accept `completed` only as a real boolean and `title` only as a non-empty string. Without them, Mongoose casting would silently save `"true"`/`1` as `true`, `null` as `null`, and `123` as `"123"`.
- **Task ownership:** `Task.user` (ObjectId, `ref: "User"`, required) is always set from `req.user.id`, never from the request body. Every task service function takes `userId` and queries `{ _id: id, user: userId }` (or `{ user: userId }` for lists). Another user's task gives 404, not 403, so the response doesn't reveal whether that ID exists.

## Conventions

Code comments are written in Roman Urdu/Hindi, explaining the "why". Match this style when adding comments.
- **Plaintext passwords must never appear** in the DB (bcrypt cost 12 only), in logs (the logger prints method and URL, never bodies), in API responses (`User.toJSON` strips `password` and the token fields), or in JWTs (the payload is `{ sub, iat, exp }`).
