# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Two separate apps:
- **`backend/`**: Tasks REST API built on Express 5 + Mongoose 9 (MongoDB), CommonJS, with JWT auth (bcryptjs + jsonwebtoken). No build step or linter. Tests are in `backend/test/` (`node:test`).
- **`frontend/`**: React + Vite SPA (ESM) with react-router v7, axios and **Tailwind CSS v4** (`@tailwindcss/vite`), for using register (with the email verify code), login and task CRUD in the browser.

**`README.md` is stale:** it still describes the old email-link flow (`GET /verify/:token`, `/verify/resend`, `APP_URL` for links). Trust this file and the code over it. The root `package.json` (just `axios`) is a leftover; each app has its own `package.json`.

## Commands

Backend (run from `backend/`):
- `npm run dev`: run with `node --watch` (auto-restart on file changes)
- `npm start`: run normally
- `npm test`: runs `test/*.test.js` with `node:test` (`auth.test.js`, `tasks.test.js`, `lockout.test.js`, `avatar.test.js`, and `ratelimit.test.js`, the only one with real limiters via `setupTestApp(name, { realLimiters: true })`; shared setup in `test/helpers.js`). It needs MongoDB, but each file uses its **own database**, `<MONGO_URI db>_<name>_test`, because `node --test` runs files in parallel. It asserts the `_test` suffix before dropping it. The email service and IP rate limiters are stubbed, so no real email is sent; the per-user 3-codes-per-hour DB limit is real.
- Single file: `node --env-file=.env --test test/auth.test.js`. Single test: add `--test-name-pattern="<regex>"` (test names are Roman Urdu strings, e.g. `"squatting"`).

Both use Node's built-in `--env-file=.env` (no dotenv package), so `backend/.env` must exist with `PORT` (default 3000), `MONGO_URI`, `API_KEY` and `JWT_SECRET`, plus the optional `SMTP_USER` and `SMTP_PASS` for real emails.

Frontend (run from `frontend/`):
- `npm run dev`: Vite dev server on http://localhost:5173
- `npm run build`, `npm run lint` (oxlint)

`frontend/.env` must contain `API_KEY` with the same value as the backend's.

Every API request needs an `x-api-key` header. `/tasks` routes also need `Authorization: Bearer <token>` from `POST /auth/login`:
```
curl -H "x-api-key: $API_KEY" -H "Authorization: Bearer $TOKEN" http://localhost:3000/tasks
```

## Frontend structure

**Styling = Tailwind classes in JSX; don't write custom CSS rules.** `src/index.css` holds only `@import "tailwindcss"` and the theme: `--app-*` colour variables (light, plus dark under `prefers-color-scheme`), mapped in `@theme inline` to `bg`, `card`, `text`, `muted`, `border`, `primary`, `success-*` and `error-*`, so you write `bg-card`, `text-muted`, `border-border`. It also sets `--text-sm`/`--text-xs` line-height to `normal`. `index.html` `<body>` has `bg-bg font-sans leading-[normal] text-text` (browser default line-height; Tailwind's 1.5 makes everything taller). Repeated class sets live in `src/ui/styles.js`: `card`, `title`/`titleText`, `form`, `field`, `label`, `input`, `muted`, `hint`/`hintText`, `link`, `cn()`, and `button({ variant: 'primary'|'secondary', size: 'md'|'compact'|'sm', weight: 'semibold'|'medium' })`. **Don't append a class for a property the base already sets** (for example `cn(title, 'mb-0')` or `cn(hint, 'text-error-text')`). Tailwind doesn't decide which one wins, so use an option or the no-margin/no-colour variant (`titleText`, `hintText`) instead.


Under `frontend/src/`, the layers mirror the backend:
- **`api/`**: `axios.js` is the single axios instance (`baseURL: '/api'`). A request interceptor reads the token **directly from `localStorage`** through `utils/helpers.loadSession()`, not from context: React runs child effects before parent effects, so Dashboard's first request would otherwise go out without a token. Before each request, if the access token has expired it refreshes first. On a 401 for a request that carried a token, it refreshes once (`_retried`) and retries. Refresh is **single-flight** (a shared `refreshPromise`), so parallel 401s trigger one refresh; the old token would be rotated away otherwise. Refresh uses bare `axios.post('/api/auth/refresh')`, which skips the interceptors. If the refresh fails, it calls `onUnauthorized` (registered via `setAuthHandlers`). A 401 on login (wrong password) has no token, so it never refreshes. `utils/helpers.loadSession()` keeps sessions whose access token has expired, because refresh can revive them. `authApi.js` and `taskApi.js` are thin wrappers that return `data`.
- **`context/AuthContext.jsx`**: `AuthProvider` (session state, `login`, `logout(reason)`, `notice`). It registers `onRefreshed` (updates state) and `onUnauthorized` (clears the local session with a "Session expired" notice). User-initiated `logout()` also calls `POST /auth/logout`. The context object and the `useAuth()` hook live in `hooks/useAuth.js`; keeping them out of the provider file keeps Vite fast refresh working (oxlint `only-export-components`).
- **`pages/`**: `Login`, `Register`, `Dashboard` and `NotFound`. Routes are in `App.jsx`: `/` redirects to `/dashboard`, which is wrapped in `components/ProtectedRoute`, which redirects to `/login` when there's no token. Login and Register redirect to `/dashboard` when already logged in.
- **`components/`**: `Navbar`, `TaskItem`, `TaskForm`, `Loader`, `Alert` (`{ ok, status, text }`, built by `helpers.toAlert(error)`), and `PasswordInput` (password field plus a "Dikhao/Chhupao" button, used on Register and Login, so a browser-suggested or mistyped password becomes visible; `<label htmlFor>` with a `useId` id and the button outside the label, so the field's accessible name is just "Password". Email and code inputs are linked the same way), `VerifyEmail` (6-digit code input plus a "new code" button with a 60s countdown, started after a resend, a 429, or a just-sent code from register; on success it calls `onVerified({ token, user })`, the parent calls `login()` and navigates to `/dashboard`; it takes `email` and `password`, both from the register or login request that showed it, never from the current input, shown after a successful register (201) or on a 403 login, never on a 409, because no code is sent then). `pages/Register` has two screens: the form, and after a 201 a separate "Verify your email" screen (with "Wapas register par").
- **Dashboard:** every mutation goes through `run(action, { onNotFound })`. It has a synchronous `useRef` guard (`inFlight`), because `busy` state updates too late and three submits in the same tick would otherwise create three tasks. It clears the old alert, sets `busy` (to disable buttons) and turns errors into an `Alert`. A 404 on toggle or delete (the task was deleted in another tab) removes the row locally with a friendly message. Success alerts disappear after 3s, and toggle shows "Done/Pending: <title>". `TaskForm` has `maxLength={200}` and a live `n/200` counter. `TaskItem` has an inline title edit (✎ → input with the same limit and counter, Enter saves, Esc cancels, an unchanged title sends nothing) that calls Dashboard's `handleRename` (`PUT` with only `{ title }`). Both take the limit from `utils/helpers.MAX_TITLE_LENGTH`. `.message` and task titles use `overflow-wrap: anywhere`, so a long word doesn't make the page scroll sideways. The first load in `useEffect` sets state only in `.then` and has a `cancelled` cleanup (oxlint `set-state-in-effect`). In dev, StrictMode sends the first `GET /tasks` twice; that's expected.

## Frontend ↔ backend

The browser never calls `localhost:3000` directly. `frontend/src/api/axios.js` calls `/api/...`, and the Vite proxy in `frontend/vite.config.js` strips `/api`, forwards the request to the backend, rewrites the refresh cookie path (`cookiePathRewrite: { '/auth': '/api/auth' }`, otherwise the browser never sends it to `/api/auth/refresh`), and **adds the `x-api-key` header server-side** (read with `loadEnv` and no `VITE_` prefix). Because of this, the backend has no CORS middleware and the API key never reaches the browser bundle. Don't expose it with a `VITE_` variable.

## Backend architecture

Layered flow: `routes → (validation middleware) → controllers → services → models`. All paths below are under `backend/src/`.

- **`index.js`** first runs `config/validateEnv.js`, which checks for required `MONGO_URI`, `API_KEY` and `JWT_SECRET` (both at least 32 characters; generate the API key with `openssl rand -hex 32`), that `SMTP_USER` and `SMTP_PASS` are set together (and are **required when `NODE_ENV=production`**, because without SMTP the verification code is printed to the logs), that `MONGO_URI` starts with `mongodb://` or `mongodb+srv://`, that `PORT` and `SMTP_PORT` (when set) are integers from 1 to 65535 (an invalid value never silently falls back to the default), and that `APP_URL` is valid. It lists every problem and exits with code 1 before any DB connection. After that it connects to MongoDB, then starts the server, each in its own `try`, so a port error is never reported as "MongoDB connection failed". It exits the process if either step fails. **`app.js`** only builds the Express app, so it can be imported without starting a server.
- **Middleware order in `app.js` matters:** `helmet()` (security headers; first, so a malformed-JSON 400 from `express.json` still gets them) → `express.json` → `cookieParser` → logger → API key check (global, after the logger so rejected requests still get logged; it compares SHA-256 hashes with `crypto.timingSafeEqual`, not `!==`, and builds the expected hash lazily on the first request, because `index.js` requires `app` before `validateEnv`) → `/tasks` (with `authMiddleware`) → `authRoutes`, mounted at the root with full paths. **All auth routes live under `/auth/*`:** `POST /auth/register`, `/auth/verify-email`, `/auth/resend-verification`, `/auth/login`, `/auth/refresh` and `/auth/logout`. None have a JWT check, since login is where the token is issued. The old root paths `/register`, `/verify-email` and `/resend-verification` are aliases (`router.post([new, old], …)`, same handler and same limiter, so the alias can't dodge the limit). Everything needs the API key; there are no public routes. Because these are `/auth/` routes, the frontend's `isAuthRoute` never attaches a token or refreshes on them → `/user` (with `authMiddleware`, then `userRoutes`; auth must run before Multer because the filename uses `req.user.id`) → 404 handler → central error handler (always last).
- **Auth:** `services/authService.js` hashes passwords with bcrypt on register. On login (`POST /auth/login`, `loginLimiter`, `validateAuth`), `checkCredentials` gives a generic 401 for an unknown email or a wrong password, then 403 if the user is unverified. **Account lockout:** `User.failedLoginAttempts` and `lockUntil` live in the DB, so a lock survives a restart, and `toJSON` strips both. While `lockUntil` is in the future, login returns **423** (`LockedError`, "Try again in N minutes", plus a `Retry-After` header in seconds) **before the password check**, so even the correct password is rejected, no token or cookie is issued, and further attempts don't change the counter. A wrong password goes to `recordFailedLogin`, an atomic `$inc`. The 5th consecutive failure (`MAX_LOGIN_ATTEMPTS`) sets `lockUntil = now + 15 min` (`LOCKOUT_DURATION_MS`), resets the counter to 0 so the user gets 5 fresh attempts after the lock, and returns 423. The lock is only set if none is active, so parallel failures can't push it later. A correct password resets the counter and clears an expired lock. Unknown emails get no DB lockout (deliberately, so no fake-account state is stored) and always return 401; the IP `loginLimiter` (50 per 15 min) covers them. Known trade-offs: 423 vs 401 reveals that an account exists, and anyone who knows an email can lock it for 15 minutes. It then signs a 15-minute access JWT with `{ sub: user.id }`. **Login sends no code;** an email code is used only once, to verify the email after register. **Refresh tokens:** login also issues a random 32-byte refresh token. It's stored as a SHA-256 hash in `models/RefreshToken.js` (7 days, with a TTL index for cleanup) and sent only as an httpOnly, `SameSite=Strict`, `Path=/auth` cookie, never in the JSON body (`cookie-parser`). `POST /auth/refresh` rotates the token: it atomically revokes the old one, then issues a new access token and a new refresh token. If a revoked token comes back more than 30s after it was revoked (`REFRESH_REUSE_GRACE_MS`), that's treated as theft and revokes all of the user's refresh tokens. Within the 30s it's treated as a multi-tab race. A failed refresh deliberately does **not** clear the cookie, so a losing tab can't wipe the winner's new cookie. `POST /auth/logout` revokes the token and clears the cookie. `middleware/auth.js` verifies `Bearer` tokens: the signature against `JWT_SECRET`, `algorithms: ["HS256"]` only (so `none`, HS384/512 and RS256 are rejected), and expiry. It also **requires** `exp` and a `sub` that looks like an ObjectId (24 hex characters), because `jwt.verify` alone accepts tokens without `exp`. `signAccessToken` sets `algorithm: "HS256"` explicitly, to match. It then checks through `authService.userExists` that the user still exists, because a deleted user's still-valid access token must not keep working for 15 minutes or create ownerless tasks. A DB error goes to the handler as a 500, not a 401. Only then does it set `req.user = { id }`; the middleware is `async`. The `User` model's `toJSON` removes `password`, so it's safe to return user documents. Login gives the same 401 message for an unknown email and a wrong password, **and takes the same time**: an unknown email is compared against `DUMMY_PASSWORD_HASH`, built once at startup. In the same way, `verifyEmail` (unknown or verified account) compares against `DUMMY_OTP_HASH`, and `resendVerification` runs a dummy bcrypt, so their timing also doesn't reveal unverified accounts.
- **Email codes (`models/Otp.js`):** one document per `{ user, purpose }` (unique compound index). Right now `purpose` is only `"verify-email"`; the field exists so that a future code, such as a password reset, gets its own document and counter. `issueOtp(userId, purpose)` creates a 6-digit code with `crypto.randomInt` and stores only its bcrypt hash (cost 10, because SHA-256 of a 1-in-a-million code breaks instantly if the DB leaks), with a 5-minute `expiresAt` and `attempts: 0`. A new code overwrites the old one. The limit is 3 codes per user per purpose per hour (`windowStart`/`requestCount`), counted atomically in three steps (inside the window, new window, first create, with an 11000 retry), and it throws `TooManyRequestsError`. A TTL `purgeAt` (1h after the last request) cleans up. `consumeOtp(userId, purpose, otp, invalid)` first reserves an attempt atomically (`attempts < 5`, not expired, `$inc`), then runs `bcrypt.compare`. If there is no active code (expired, 5 attempts used, already consumed), it still compares against `DUMMY_OTP_HASH`, so the timing doesn't reveal whether the account has an active code. The 5th wrong attempt unsets the hash, and a correct code is consumed atomically (single use, so parallel requests can't both succeed). Every failure throws the caller's `invalid` error. `services/emailService.js` `sendOtpEmail(email, otp, purpose)` prints the code to the console **only when SMTP is not configured** (`[dev — SMTP not configured]`); with SMTP the code is never logged. Otherwise it emails through Nodemailer (default host `smtp.gmail.com:465`, `config.smtp`). Callers don't `await` it, so the response doesn't wait for SMTP (1–4s). A failed send is logged, not thrown. SMTP gives up after a 10s connection timeout, and an App Password pasted with spaces gets the spaces stripped in config.
- **Email verification (code, no links):** register uses `validateRegister` (`newPasswordError()`, see Validation below; login keeps the looser `validateAuth`) and bcrypt cost 12. It stores `isVerified: false`, then sends a `"verify-email"` code (no links, no `GET /verify/:token`, no HTML pages). **Only a verified account gives 409.** Registering an email whose account is still unverified does **not** give 201 (no new account was created). It gives 200 with the generic `{ message: "If an account exists for this email, a verification code has been sent." }` and sends a new code. **It does not overwrite the password**, so nobody can change another person's password by registering again; the final password is set at verify anyway. After 3 codes per hour it gives the same 200 and sends no email: a 429 would reveal an unverified account, and staying silent also stops mail spam. The frontend shows the verify screen for both 201 and 200. All lookups use `normalizeEmail()` (trim + lowercase), so `QA@X.com ` and `qa@x.com` are the same user. Without this, someone could pre-register another person's email and lock the owner out. `POST /verify-email` (`{ email, otp, password }`, `validateOtpVerify`, `otpVerifyLimiter`) **sets the password at verify time.** Only the email owner sees the code, so the final password is always theirs. If the password were fixed at register, an attacker could pre-register someone else's email, the owner would enter the code, and the attacker's password would then log in. Every failure returns 400 "Invalid or expired code": unknown email, already verified, wrong, expired or used code. So it doesn't reveal account state. On success it sets `isVerified: true` and the new password hash, and **logs the user in**: it returns `{ message, token, user }` and sets the refresh cookie, exactly like login. The code and the password together already prove the user, so we don't ask for the password again. The frontend sends the password from the register or login form along with the code. `POST /resend-verification` (`{ email }`, `validateEmail`, `resendLimiter`) issues a new code, and the old one stops working. **Rate limiting:** `middleware/rateLimit.js` (express-rate-limit, in-memory, keyed by IP) gives `resendLimiter` 5 per 15 minutes, `resendEmailCooldown` 1 resend per **email** per 60s (keyed by the normalized email and mounted after `validateEmail`; it applies whether or not an account exists, so its 429 reveals nothing), `registerLimiter` 10 per hour, `loginLimiter` 50 *failed* logins per IP per 15 minutes (against password spraying across many accounts; one account is protected by the 5-attempt lockout, and a limit of 10 let one person's typos block a whole shared network, correct passwords included; its message says "from this network" with the real minutes left, so it isn't confused with the account's 423), and `otpVerifyLimiter` 10 *failed* `/verify-email` code attempts per 15 minutes. Both of the last two use `skipSuccessfulRequests` and are mounted before validation. All return `429 { message }`. On top of that, the per-user limit of 3 codes per hour lives in the DB. **Resend always returns the same 200 message** (`RESEND_RESPONSE`) for an unknown email, an already-verified account, a sent code and a reached 3-per-hour limit (it swallows the 429), so it can't be used to discover which emails are registered or verified. Behind a reverse proxy in production, set Express `trust proxy`, or every client shares one IP. Login returns 403 for unverified users. The check runs after the password check, so a wrong password still gives the generic 401 and does not reveal verification status.
- **Config:** `process.env` is read only in `config/index.js`. Everything else imports that config module. `config.otpTtlMs` (5 min) is the single source for the code's DB expiry and the "expires in N minutes" email text (`emailService.otpEmailContent`). `config.appUrl` (from `APP_URL`, falling back to `http://localhost:${PORT}`, trailing slash removed) now only decides whether the refresh cookie is `Secure` (https).
- **Separation of concerns:** controllers handle req/res and never touch Mongoose. All DB access goes through `services/`.
- **Error handling:** controllers wrap their logic in try/catch and call `next(err)`. Services and middleware throw the Error subclasses in `utils/` (`BadRequestError` 400, `UnauthorizedError` 401, `ForbiddenError` 403, `NotFoundError` 404, `ConflictError` 409, `LockedError` 423, `TooManyRequestsError` 429), each carrying a `statusCode`. If an error has `retryAfterSeconds`, the handler also sets a `Retry-After` header. `middleware/errorHandler.js` turns malformed JSON bodies (`err.type === "entity.parse.failed"`) into a generic 400 "Invalid JSON in request body"; never echo that error's message, because Node's JSON parse errors include parts of the body, such as the password. It maps Mongoose `CastError` to `Invalid <path>`, and `ValidationError` to per-field messages (a `required` field keeps its own message; everything else becomes `Invalid <path>`, **never `err.message`**, because Mongoose embeds the rejected value, such as a password). MongoDB duplicate-key errors (`11000`) become a fixed 409. `multer.MulterError` has no `statusCode`, so it's mapped explicitly: `LIMIT_FILE_SIZE` → 413, `LIMIT_UNEXPECTED_FILE` (wrong field name) → 400, anything else (such as two files) → a fixed 400 "Invalid file upload."; its message is never sent. `err.message` is sent only for 4xx errors with a `statusCode`, meaning our own classes or body-parser. Everything else gets a generic 500 "Internal Server Error"; the server log records only the error name and stack frames, not the message. Every error response has the shape `{ message }`.
- **Validation is two-layered:** `middleware/validation.js` checks request bodies before they reach the controller (`validateCreateTask`, `validateUpdateTask` for PUT, `validateAuth` for login, `validateOtpVerify` for `/verify-email` (the code must be a string of exactly 6 digits), `validateRegister`, `validateEmail` for resend). Auth fields go through `stringFieldError()`: missing, `null` or empty gives "<Field> is required", and a non-string (object, array, number, or an operator like `{ "$ne": null }`) gives "<Field> must be a string". Register and verify-email share `newPasswordError()`: 8+ characters, **at least one letter (`\p{L}`) and one digit**, no leading or trailing whitespace (`"        1"` is rejected; spaces in the middle are fine), and **at most 72 bytes**. The frontend mirrors these rules in `utils/helpers.passwordRuleError`/`PASSWORD_RULES_HINT` and checks them before submitting. The 72-byte limit exists because bcrypt ignores everything after 72 bytes, so a longer password would accept any tail. This is `Buffer.byteLength`, not characters, so `é` counts as 2. Login also rejects passwords over 72 bytes with 400. Register and resend share `emailError()`, which needs the simple `x@y.z` shape; login doesn't check the format, since a bad email just gets 401. The Mongoose schema rules also apply on updates because `findOneAndUpdate` is called with `runValidators: true`.
- **Express 5 specifics:** `req.body` is `undefined` when no body is sent, so code guards with `req.body || {}`. `app.listen` reports startup errors (such as a port already in use) through its callback's `error` argument.
- **Partial updates:** PUT only changes fields that are `!== undefined`, so `completed: false` still counts as a real update. `validateUpdateTask` requires at least one of `title`/`completed`. Both task validators accept `completed` only as a real boolean and `title` only as a non-empty string of **at most 200 characters after trim** (`titleError`; the schema also has `maxlength: 200`, and the frontend `TaskForm` has `maxLength={200}`). Without them, Mongoose casting would silently save `"true"`/`1` as `true`, `null` as `null`, and `123` as `"123"`.
- **Task ownership:** `Task.user` (ObjectId, `ref: "User"`, required) is always set from `req.user.id`, never from the request body. Every task service function takes `userId` and queries `{ _id: id, user: userId }` (or `{ user: userId }` for lists). Another user's task gives 404, not 403, so the response doesn't reveal whether that ID exists.
- **Avatar upload (`POST /user/upload-avatar`):** API key + Bearer access token, `multipart/form-data` with one file in the field `avatar`. Files: `config/upload.js` (Multer), `routes/userRoutes.js`, `controllers/userController.js`, `services/userService.js` (`setAvatar`), `User.avatar` (String, default `null`, returned by `toJSON` because the frontend needs it), and the Multer branch in `errorHandler.js`. Multer `diskStorage` writes to `config.avatarUploadDir` (`backend/uploads/avatars/`, created at startup, **gitignored**); the service deletes old files from the same path, so it's defined only in config. The filename is `<userId>-<timestamp>.<ext>`, **never `originalname`**, and the extension comes from the declared MIME type (`allowedTypes`: `image/jpeg` → `.jpg`, `image/png` → `.png`, `image/webp` → `.webp`). `fileFilter` rejects everything else (HTML, SVG, PDF…) with `BadRequestError` 400 "Avatar must be a JPEG, PNG or WebP image." before anything is written to disk. Limits: 2 MB (`LIMIT_FILE_SIZE` → 413) and 1 file. A missing file gives 400 "Avatar file is required" (Multer doesn't error, `req.file` is just absent). `setAvatar` uses one atomic `findByIdAndUpdate` with `returnDocument: "before"` so it gets the previous path without a read-then-save race. After a successful update it deletes the old file. On a DB error or a missing user it deletes the new file. Old files are deleted by `path.basename` inside the avatars folder only, so a bad DB value can't reach outside it. **Not done yet, on purpose:** uploads are **not served** (no `express.static`; don't add it without stronger validation), and the type check trusts the declared `Content-Type`; there's no magic-byte check, so `evil.html` sent as `image/png` is stored, but as `.png`. Tests: `test/avatar.test.js` (it uses the real folder and deletes only the test user's `<userId>-*` files).

## Conventions

Code comments are written in Roman Urdu/Hindi, explaining the "why". Match this style when adding comments.
- **Plaintext passwords must never appear** in the DB (bcrypt cost 12 only), in logs (the logger prints method and URL, never bodies), in API responses (`User.toJSON` strips `password`, plus link-era token fields that old users may still have), or in JWTs (the payload is `{ sub, iat, exp }`).
- **Delete test data after every test.** Any manual, browser or script test against the real DB (`tasksdb`) must, once it finishes, delete everything it created: the users plus their `tasks`, `otps` and `refreshtokens`, their avatar files in `backend/uploads/avatars/` (named `<userId>-*`), and any leftover `*_test` database. Then query the DB to confirm nothing is left, and report what was deleted. Give test users recognisable emails (`*@example.test`, or Gmail plus-addresses such as `+qa-*`) so they are easy to find. `npm test` uses its own `*_test` databases and drops them itself. Ask before deleting test data that someone else (QA or the user) created, and never delete the owner's real accounts.
